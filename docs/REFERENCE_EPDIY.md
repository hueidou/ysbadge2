# 参考项目对照：vroland/epdiy 与 tsl0922 蓝牙墨水屏日历（2026-10-23）

调研对象：

- <https://github.com/vroland/epdiy> —— ESP32(-S3) 墨水屏驱动板 + 驱动库（文档在 Read the Docs）
- <https://epdiy.cn/> —— **与 vroland/epdiy 无关**（域名撞名）。它是 tsl0922
  《蓝牙墨水屏日历》的网页上位机；固件 <https://github.com/tsl0922/EPD-nRF5>，
  硬件为立创开源硬件平台上的 nRF51822 驱动板 + 4.2 寸三色/黑白墨水屏。
  同一上位机另有 tsl0922.github.io/EPD-nRF5/ 等镜像，epdiy.cn 是带图片编辑功能的较新版本。

证据分级沿用 LESSONS.md 口径。**本文全部为 源码/他机 级**（对方公开资料），
没有任何本机 YSBadge2 实测；涉及本机的结论都标注来源章节。

---

## 1. vroland/epdiy：架构对照，背景价值为主

| 维度 | vroland/epdiy | 本项目 YSBadge2 | 参考价值 |
| --- | --- | --- | --- |
| MCU | ESP32-S3（有 PSRAM，V7 板） | PHY6220 Cortex-M0，约 32KB RAM | 他们有富余内存，**从不讨论压缩**——反衬我们 32KB 困境的根源是 MCU 而非屏（PROTOCOL.md §6.0） |
| 面板 | 仅灰度 4bpp（16 灰），README 兼容表**无 ACeP/七色** | 800×480 七色 ACeP 类 | **反面证据**：开源生态对七色墨水屏支持稀缺，本项目七色协议逆向处于领先位置 |
| 刷新 | LUT 驱动（如 `EPD_LUT_64K`）、VCOM 需逐屏校准、局部刷有残影（troubleshooting 明示） | 固件黑盒，实测两次刷新间隔约 30s、期间吞数据 | 背景知识：我们观测到的刷新吞数据/闪屏有同一物理来源（波形与像素回转），非协议 bug |
| 数据通路 | I2S（ESP32）/ LCD 总线（S3）直推帧缓冲 | BLE 压缩流 → MCU 侧 LZ77 解压 → 推屏 | 架构对照：本地大总线 vs 窄带无线，约束完全不同 |
| 无线 | WiFi/BLE 是芯片能力，**无 BLE 传图协议** | 完整 BLE 协议（ff01-ff04）已逆向 | 协议层无可抄内容 |
| 维护 | 活跃（2025-12 → 2026-08，IDF 6.0 支持等） | — | 工程实践（CI/文档站/组件化）可参考，与协议无关 |

**结论**：无可直接移植内容。价值 = 波形/LUT/刷新物理背景 + 两条印证（32KB 是 MCU 级限制、
七色开源支持稀缺）。

## 2. tsl0922 蓝牙墨水屏日历（EPD-nRF5 / epdiy.cn）：最近缘同类项目

### 2.1 硬件与生态（源码/他机）

- nRF51822 / nRF52810 / nRF52811 + 4.2 寸 400×300 **三色（黑白红）或黑白**屏；
  驱动 IC 覆盖 UC8176 / UC8276 / SSD1619 / SSD1683 / JD79668（价签拆机生态，与盒马 DA14585 价签同源）
- QFAC 后缀 = **32KB RAM** 版本（官方明确建议选 256K Flash + 32K RAM 版）
  —— 与我们 PHY6220 同级的 32KB RAM MCU 跑 BLE 传图
- 4.2 寸三色屏**传图约 8s**（推断为裸流：400×300 2bpp ≈ 30000 B，244 B/包 × 40ms ≈ 5s + 开销）
- 蓝牙名 `NRF_EPD_XXXX`；支持 **BLE OTA**；2 分钟无蓝牙连接进深睡（微安级），
  NFC/无线充电器/按键唤醒；日历模式设备端渲染，每晚 00:00 自动更新

### 2.2 与现有结论互相印证（他机观测 vs 本机结论）

| 他们（他机） | 我们（本机，来源章节） |
| --- | --- |
| 32KB RAM 的 nRF51822 整帧缓冲 30000 B 刚好装下，所以不压缩、裸流 8s | 192000 B 帧装不进 32KB → 必须 LZ77 + 流式；§6.0 "BLE 接收路径一次性缓冲"的量级佐证 |
| 深睡 + 需唤醒才重新广播 | §9.1 扫描不到 ≠ 失联；桌牌唤醒后广播窗口短、40s 窗口才稳 |
| 上位机只支持 Chrome/Edge/Bluefy（Web Bluetooth） | 网页版同样的浏览器矩阵（README 网页版章节） |
| 上位机参数栈：FS 抖动 + 强度 + 亮度 + 对比度 + 裁剪 + 画笔/文字/模板 | IMAGE_PROCESSING.md 的参数体系；网页版的文字模式/预设/导出是同一产品方向 |
| 时钟模式"目前使用全刷实现，不建议长期开启" | 全刷成本高的工程共识；我们侧对应"两次刷新间隔约 30s，快发吞第二张" |

### 2.3 可行动项（分级）

**待验（有明确价值，按 32KB 预案同级别纪律执行：单变量、可断电恢复、先离线确认）**

1. **时间同步 / 设备端渲染命令是否存在**：他们有"日历模式 = App 同步本地时间 + 设备渲染日历"。
   我们目前只确认 INIT/PIC_INFO/UPDATE 与两个未知帧 0xA0/0xA1（PLAN_32KB_BLE.md Step 1-3）。
   若胸牌要当时钟/日历，这是下一步 probe 方向——注意 INIT 的 `epd_index` 非法值会瞬间挂机（§9）。
2. **识别屏体驱动 IC**：HARDWARE.md §7（2026-10-23）已由规格匹配推断屏体为
   **GDEY073D46**（7.3 寸 ACeP 800×480 七色），控制器疑似 **SPD1656 家族**（cale-idf 实测行为一致，
   Adafruit CircuitPython 有 spd1656 驱动）。仍待读 FPC/COG 丝印确认。
   注意板上 FPC 座约 32 pin 与数据手册 50 pin 不一致，也要顺带核对。
   该屏满刷固定 32s、不支持局刷——本机「约 30s 吞数据窗口」的物理解释（PROTOCOL.md §6.0 已补）。

**可借鉴（产品层，非协议）**

- 深睡/唤醒、OTA、每日自动更新的产品形态——我们设备**无 DFU 恢复通道**（§9），
  OTA 类想法在取到固件前不要碰；深睡唤醒与我们已观测到的广播窗口行为一致，无需动作。

**不适用（不要照搬）**

- 裸流传图（我们 ctype=0 实测不刷新且卡死 GATT，LESSONS.md §1）
- 三色屏抖动工艺（我们七色 ACeP，误差扩散行为不同，IMAGE_PROCESSING.md §3）
- ESP32 驱动板架构（MCU/RAM/总线全不同）

## 3. 结论

- **vroland/epdiy**：背景知识 + 反面证据（无七色、无 BLE 协议），无可移植内容。
- **tsl0922 / epdiy.cn**：最近缘同类项目，互相印证 5 条现有结论（32KB 量级、广播窗口、
  浏览器矩阵、参数栈、全刷成本），产出 2 个待验方向：时间同步命令 probe、屏体驱动 IC 识别。
