## 1. compress_type=0 未压缩通道：本机验证不成立（2026-10-21）

对方主张用 PIC_INFO 的 compress_type=`0` 走原始数据：

    INIT:      [00, 06, epd_index]
    PIC_INFO:  [01, 00, 00, EE, 02, 00]      192000 = 0x0002EE00，小端
    PIC_DATA:  192000 字节原样写 ff02，244 B/包，40 ms 间隔 → 787 包

源码确实有这个分支（BluetoothTool.java:41/55 传 `pic_data.length`），对方也声称在自有设备上跑通。
但**本机 YSBadge2 实测不成立**，六组对照如下：

| # | 帧 | 数据 | FF04 通知 | 屏幕 | 设备状态 |
| ---: | --- | --- | --- | --- | --- |
| 1 | PIC_INFO(0, 192000) | 787 包 / 39.3 s | 中途 25 s 一条 `02 00 00` | **不刷新** | 正常 |
| 2 | 对照：PIC_INFO(1, 46216) | 24 包 / 1.2 s | 发完 3 s 一条 `02 00 00` | **正常刷新** | 正常 |
| 3 | PIC_INFO(0, 192000) + 收通知暂停 + UPDATE | 787 包 / 44.3 s | `02 00 00`@4.1 s、`00 02`@7.3 s | 不刷新 | UPDATE 写入失败（Unreachable），随后停止广播 |
| 4 | 对照：压缩版标记图 | 20 包 / 0.9 s | 无 | **正常刷新** | 正常 |
| 5 | 未压缩标记图（同图） | 787 包 / 36.9 s | `02 00 00`@4.1 s | **不刷新** | 仍在广播 |
| 6 | PIC_INFO(0, 1536000)（长度按比特） | 787 包 / 36.9 s | `02 00 00`@7.9 s | 不刷新 | 正常 |
| 7 | PIC_INFO(0, 192000) + UPDATE | 787 包 / 36.9 s | `02 00 00`@4.2 s | 不刷新 | UPDATE 写入失败，GATT 卡死 |

结论：
1. **本机固件不接受 compress_type=0**：数据全收、连接不断，但不刷新，说明被当作异常路径丢弃。
2. **长度字段也不是“按比特解释”**：声明 1536000 与 192000 表现一致，说明设备根本没进入解码。
3. **192000 字节会把 GATT 弄挂**：3 次未压缩里有 2 次随后写 UPDATE 失败、设备需断电重启
   （对照组从未出现）。与“接收缓冲只有约 32 KB”的推断一致——未压缩数据直接打爆接收侧。
4. 对照（压缩模式）每次都正常刷新，且用同一张标记图做了 A/B，排除了“刷了但画面一样”。

因此：**照片抖动仍然不可用**，抖动只能在压缩模式 ≤ 262144 bit 内做。

## 2. PIC_INFO 长度字段的语义随模式变化

| compress_type | len0..len3 含义 | 单面典型值 |
| ---: | --- | ---: |
| 0 | 原始字节数 | 192000（0x0002EE00） |
| 1 | 压缩后比特数 | 约 250432 |

写死“比特数”会让未压缩模式少发 7/8 数据。编码时按模式分支，不要共用一个变量名。

---

## 3. 抖动是否超限取决于内容，不是一刀切（本机）

同一套 7 色量化 + 本项目 LZ77，压缩后的比特数：

| 内容 | no-dither | FS 抖动 |
| --- | ---: | ---: |
| 对方日历截图（纯色块 + 文字） | 93150 bit / 11.4 KB | 103719 bit / 12.7 KB |
| 合成渐变图（模拟照片） | 30153 bit / 3.7 KB | 992785 bit / 121.2 KB |

结论：**UI、表格、二维码、文字类内容抖动几乎不涨体积**（平坦区域误差为 0，抖动不产生噪点），
只有照片类连续色调才会指数膨胀。所以策略是“按内容选”，而不是“全局禁抖动”。

## 4. BLE 交互健壮性差异（可直接移植）

| # | 对方做法 | 本项目现状 | 收益 |
| ---: | --- | --- | --- |
| 1 | `inspect` 子命令只读枚举 GATT，打印每个特征的 properties 与 max write 长度 | 无 | 换批次固件时先看再发，避免盲试 |
| 2 | 读 `max_write_without_response_size`，超过就自动降分包 | 写死 `mtu_size - 3` | Windows MTU 247 时两者一致，但跨平台/跨固件更稳 |
| 3 | 按 characteristic.properties 选 write / write-without-response | 写死 `response=False` | ff03 用带响应写能拿到失败信号 |
| 4 | 已知地址时用 `find_device_by_address` 拿到即连，不等满扫描窗口 | 直接 connect | 桌牌唤醒后广播窗口短，满窗口扫描易错过 |
| 5 | `BleakError` 单独兜底，提示去系统设置开蓝牙权限 | 无 | 失败信息可执行 |
| 6 | 纯函数 + 无硬件单测：INIT 字节、PIC_INFO 小端、纯白屏全 0x11、半字节序 `01 23 45 60`、写模式选择 | 零测试，`compress/decompress` 裸奔 | 回归防护 |

单测样本可直接复用对方的白屏断言：纯白 800×480 打包后 192000 字节全为 `0x11`。

## 5. 不要照搬的

- **macOS identifier 逻辑**：CoreBluetooth 用 UUID 不暴露 MAC，本项目在 Windows 直接按 MAC 连，套用反而绕远。
- **硬编码 244 B / 40 ms**：对方没说明 40 ms 的依据，也没验证过更小间隔。本项目已实测可用，保留但别当成协议常量写进文档。
- **未测 index 7 未压缩**：384000 字节、约 63 s，对方只测了单面；本项目“两次发送间隔 30 s”的经验比它完整，不要因为对方没提就放松。
- **无发送前体积校验**：对方靠“从不抖动”隐式规避。本项目已有 `compressed ... bits` 输出，保留。
- **`nearest_palette_index` 的 `min_distance = 195076`**：这是“永不失败”的哨兵值（RGB 平方距离上限 195075），能跑但极难读，别抄写法。

## 6. 待验证清单

已关闭：

- ~~compress_type=0 单面 A~~ → 不刷新，见 §1，通道关闭；
- ~~未压缩 index 7 / 未压缩后的 30 s 间隔~~ → 随通道关闭一并作废。

仍待验证（按价值排序）：

1. 40 ms 能否降到 20 ms（理论上 244 B 只占约 2 个 connection interval），缩短压缩模式耗时。
2. 244 B 是否已是上限（Windows MTU 247 → 247-3=244，大概率到顶）。
3. 32 KB 上限的精确边界（现有证据：成功 32024 B、失败 39186 B，中间未二分）。
4. 双面同显 index 3 是否等于单次 192000 B 还是两次传输 —— 影响“一面图另一面复用”的策略。
5. **BLE 上复刻 NFC 的批量握手能否突破 32 KB**（2026-10-21 新增）：NFC 路径用
   START_SENDING(0xA0) + 轮询 BUFFER_EMPTY(0xA1) 做 9360 B/批的分批接收（PROTOCOL.md §6.0），
   证明设备能收任意大的图；BLE 固件是否实现同样握手未知。**风险高**（可能把设备打进失联状态），
   要做先确保可断电重启，且需单变量探针 + 全程 ff04 记录。

## 7. 落地顺序（按 2026-10-21 结论调整）

未压缩通道关闭后，照片抖动无解，收益重心转向“在 32 KB 内把画面做干净”：

1. 量化/预处理现代化：PIL `quantize` 快路径、EXIF 方向、透明底铺白（见 `IMAGE_PROCESSING.md` §3/§4）。
2. 出图链路：HTML → 截图 → `--no-dither`，桌牌最实用场景且体积仅约 11 KB。
3. 发送前体积守门：编码后立刻算 bits，超限直接报错而不是静默白发 30 s。
4. 协议单测（纯函数，无硬件）。
5. 可选实验：局部抖动（只对照片区做弱抖动，其余走平铺），把 12 KB 量级的余量用起来。
