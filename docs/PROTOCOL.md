# YSBadge2 墨水屏 BLE 投图协议（实测确认版）

设备：YSBadge2，MAC EE:96:BB:1E:05:28，双面 800x480 七色墨水屏。
本文件为实机验证后的确认版本，替代早期仅基于静态反编译的推测版本（见文末勘误）。

## 1. BLE GATT
- 服务 0000ff01-0000-1000-8000-00805f9b34fb
- write_pic 0000ff02-0000-1000-8000-00805f9b34fb（write-without-response）
- write_cmd 0000ff03-0000-1000-8000-00805f9b34fb（write / write-without-response）
- notify   0000ff04-0000-1000-8000-00805f9b34fb（read / notify）
- 另有厂商服务 933d87bd-63d6-14ab-e911-f312d435317e（App 未使用，非投图必需）

## 2. 命令帧（BLE，无 CRC）
    INIT:      [00, epd_type, epd_index]
    PIC_INFO:  [01, compress_type, len0, len1, len2, len3]   （len 小端，含义随模式变，见下）
    PIC_DATA:  写 ff02 的原始字节流，按 MTU-3 分块，约 40ms/块
    UPDATE:    [03, 00]（可选；NFC 路径会发，BLE 官方 App 不发）

epd_type 默认 6（EPD_TYPE_NCOLOR_0730，800x480）。
epd_index：1=屏A，2=屏B，3=A&B同显，7=A&B异显（pic_data = 图A || 图B）。

len 字段的含义由 compress_type 决定，两者不可混用：

| compress_type | len 含义 | 单面典型值 |
| ---: | --- | ---: |
| 0 | 原始字节数 | 192000（0x0002EE00） |
| 1 | 压缩后比特数 | 约 250432 |

依据：reference/apk/apk_src/sources/com/app/ysbadge/EPD_Config.java:71-77 的 get_EPD_CMD_SEND_PIC_INFO（crc_enable=false 分支，
帧固定为 {1, compress_type, len0..len3}）；BluetoothTool.java:41-47 在 compress_type==0 时传
pic_data.length、==1 时传 LZ77 比特数；Dalvik 模拟器输出 INIT(type6,index1) = 00 06 01。

**2026-10-21 实机确认**：按比特数声明可正常刷新（`_verify/send_probe.py`：INIT `00 06 01` /
PIC_INFO `01 01 88 b4 00 00` = 46216 bit，ff04 回 `02 00 00`，24 块发完即刷新）；
按字节数声明则屏幕无变化、设备随后失联（停止广播，断电重启才恢复）。两者不可混用。

## 3. 发送时序（App 与实测）
1. 连接并协商 MTU（App 请求 256，Windows 实测 247）
2. 使能 ff04 通知
3. 写 INIT 到 ff03
4. 写 PIC_INFO 到 ff03
5. 等待约 0.5s
6. 把压缩数据（或未压缩的 192000B）分块写入 ff02（约 40ms/块）
7. 设备收齐后自动刷新；断开

注意：两次刷新之间需间隔，设备刷新期间收到的数据会被忽略（实测连续发送会丢第二张）。

## 4. 图片编码（NColor 4bit）
- 画布 800x480（ARGB）
- 每像素取最近调色板色：欧氏距离，严格小于才替换（同距取索引小者）
- 调色板（索引 = 4bit 码）：
    0 黑 (0,0,0)   1 白 (255,255,255)   2 绿 (0,255,0)   3 蓝 (0,0,255)
    4 红 (255,0,0) 5 黄 (255,255,0)     6 橙 (255,128,0)
- 行优先，两个像素打包一字节：高半字节=偶数列，低半字节=奇数列
- 输出固定 192000 字节

## 5. LZ77 压缩
- 滑动窗口 1024，最小匹配长度 2
- 匹配偏移 10bit；长度用 Golomb(m=3)；字面量 9bit（1 flag + 8 data）
- 输出比特数即 PIC_INFO 的 len（compress_type=1 时；未压缩模式填字节数）
- 复刻实现见 epd_send.py 的 compress()；配套 decompress() 用于逐字节自检
- 实现用 2 字节前缀索引做候选筛选（长度为 1 的匹配本就不编码），输出比特流与原暴力实现逐字节一致

### 5.1 位级格式（2026-10-21 补齐，字节内 LSB 优先）

    字面量： 0 | 8 bit 数据（LSB 先发）                        = 9 bit
    匹配段： 1 | 10 bit 偏移 | q 个 1 + 一个 0 | 3 bit 余量 r    = 15+q bit
            匹配长度 = (q<<3) + r + 1

- 偏移基准是**窗口起点**（offset = 匹配位置 - max(0, i-1024)），不是当前位置；
  解压时 src = max(0, 已输出长度-1024) + offset。这一点弄反会解出乱码。
- 最短匹配 2 B 即值得编码：匹配花 15 bit，两个字面量要 18 bit；长度 1 不编码（best>1）。
- Golomb q 无上界（一元码），所以匹配长度也不设上限；窗口固定 1024 B。

走查实例 b"AAAA"（自检用例，实测 33 bit / 5 B）：

    i=0  窗口空            -> 字面量 'A'                      9 bit
    i=1  窗口仅 1 B，凑不出 2 B 匹配 -> 字面量 'A'            9 bit
    i=2  窗口内找到 "AA"，偏移 0，长度 2 -> q=0, r=1        15 bit
                                                  合计    33 bit

### 5.2 压缩在设备侧解，不在 PC 侧解（2026-10-21 确认）

设备收到的是压缩位流，由固件解压后推给屏；"直接可用"的原始路径（ctype=0）在本机不刷新。证据：

- 源码：NfcDataHandler.java:262 每批发完打印 "Start Decompress & Sending..."，随后
  :274-288 轮询 EPD_CMD_BUFFER_EMPTY(0xA1) 等设备解压排空——App 作者明确知道设备要解压；
- 本机：ctype=0 声明 192000 B 原始数据，数据全收但从不刷新（§6.1），说明解码路径只吃压缩输入；
- 本机（双向印证）：本项目独立实现的 compress() 产出被设备正确解出、画面正确
  （_verify/send_probe.py 2026-10-21）——PC 侧压缩器与设备侧解压器位级兼容。

选这种"土法"格式的原因（推断，与上述吻合）：无 Huffman/熵编码，解压器只需 1 KB 窗口、
顺序输出、回溯不超窗口，Cortex-M0 上几 KB RAM 即可运行；代价是压缩率平淡。

## 6. 实测约束（压缩模式）
- payload 上限约 262144 bit（32KB），超出则设备静默丢弃（整张不刷新）
- 实测成功：250432 / 256189 / 249282 bit（原版、反色、增强，均 <= 32KB）
- 实测失败：313488 / 341398 / 506621 / 1244281 bit（Bayer、FS 抖动等 > 32KB）
- 结论（限定于压缩模式）：照片类抖动不可用；官方 App 的 dither_enable 恒为 false，故其照片约 31KB 天然在限内
- 补充（本机实测）：抖动是否超限取决于内容。800×480 日历截图 no-dither 93150 bit、开抖动 103719 bit，
  均在限内；只有照片类连续色调会膨胀到 155KB 量级。详见 IMAGE_PROCESSING.md §7

### 6.0 这 32KB 是固件的限制，不是屏幕的限制（2026-10-21 定性）

结论：**BLE 接收路径的一次性缓冲上限，根源是主控 RAM，与面板无关。** 证据分级如下。

| # | 证据 | 级别 |
| --- | --- | --- |
| 1 | 262144 bit = 32768 B = 2^15，整齐的二进制倍数——缓冲区尺寸的特征；屏的天然上限应是帧缓冲 192000 B 而非 32KB | 本机 |
| 2 | 未压缩 192000 B（正好一块完整帧缓冲）数据全收但从不刷新、还把 GATT 卡死（§6.1）→ 接收侧从来没有那么大缓冲 | 本机 |
| 3 | 源码：NFC 路径 PACKET_SIZE=240（NfcDataHandler.java:76），每 39 包发一次 START_SENDING(0xA0) 再轮询 BUFFER_EMPTY(0xA1)（:260-288），即 9360 B 一批、收一批解一批推给屏再排空。**设备能接收的总量没有 32KB 限制**，只是每批受缓冲约束 | 源码 |
| 4 | BLE 路径没有 START_SENDING/BUFFER_EMPTY 握手（BluetoothTool 只有 INIT→PIC_INFO→流式写 ff02），所以整条流必须一次装进接收缓冲 → 32KB | 源码 |
| 5 | 主控 PHY6220（Cortex-M0 BLE SoC）无外部 RAM（HARDWARE.md），该级别 SRAM 几十 KB 量级，装不下 192000 B 帧缓冲；板上屏走 FPC，192KB 由**屏自己的控制器 GRAM** 持有，MCU 只需持有一批 + 1024 B 解压窗口 | 推断 |
| 6 | 第三方 macOS 示例在同协议族设备（epd_type 6）上声称跑通 192000 B 未压缩——若属实，同一块屏不设这个限 | 他机 |

（2026-10-23 补）屏体已锁定为 GDEY073D46（7.3 寸 ACeP，HARDWARE.md §7）：其数据手册明确面板集成
frame buffer 与 LUT，证据 5 由「推断」获得数据手册级佐证；且满刷固定 32s、不支持局刷——
本机实测的「约 30s 吞数据窗口」由此获得物理解释（每次上屏都是 32s 满刷）。

由此解释 "32K vs 192K 为何不矛盾"：两者从不同时存在于同一处——BLE 侧 ≤32KB 压缩流在 MCU 缓冲里，
192KB 像素在屏控制器 GRAM 里，中间由固件流式转换。压缩是强制的，因为 MCU 既不能整图缓冲，
其未压缩流式路径在本机固件上也没实现（§6.1）。

推论（待验，勿擅试）：NFC 路径证明设备分批+排空就能收任意大的图，BLE 上若能复刻
START_SENDING/BUFFER_EMPTY 握手，理论上可突破 32KB。但 BLE 固件是否实现该握手完全未知，
盲试有把设备打进失联状态的风险（需先确保可断电重启）。

### 6.2 压缩比门槛与实测阶梯

原始帧缓冲固定 192000 B，压到 ≤32768 B 才能传输，即**压缩比 ≥ 5.86 : 1**（压到原始 17.1% 以下）。
注意字面量成本是 9 bit/字节 > 原始 8 bit/字节，所以不可压缩内容会**变大**：

| 内容 | 压缩后 | 比率 | 门槛 |
| --- | --- | --- | --- |
| test_pattern（纯色块+大字） | 5,777 B / 46,216 bit | 33.2 : 1 | 过 |
| 800×480 日历截图（无抖动） | 11,644 B / 93,150 bit | 16.5 : 1 | 过 |
| 演示图两张（index 7，A\|\|B） | 22,945 B / 183,555 bit | 16.7 : 1 | 过 |
| test_pattern + 噪声 A=128 | 38,292 B / 306,333 bit | 5.0 : 1 | **差一点，拒** |
| 照片 + FS 抖动 | ~155 KB | ~1.2 : 1 | 拒 |
| 纯随机噪声图 | 192,250 B / 1,537,995 bit | 1.0 : 1 | 拒（比原始还大 0.1%） |

理论上限（全字面量）= 192000 × 9 = 1,728,000 bit。压缩率只取决于内容可预测性，
与用了几个颜色无关——噪点/渐变/细灰线/小字都会打断匹配。


### 6.3 双面的体积预算：上限作用于合并流，不是每面

**同时设置两面时，262144 bit 是两面的合计，不是每面各一份。**

- index 7（异显）：pic_data = 图A || 图B = 384000 B 原始，合并成**一条** LZ77 流压缩、一次 PIC_INFO 声明；
  源码 NfcDataHandler.java:36-39 仅 index 7 走 combineBytes(one, two)。BLE 路径同构（BluetoothTool 流式写整条 payload）。
  本机实证（2026-10-21）：两面简图（红条大字 A / 蓝条大字 B）384000 B → 7883 B / 63063 bit，33 块发完，两面正确显示。
- index 3（同显）：官方 App 与 epd_send.py 都只发**一份**帧数据（NfcDataHandler.java:40-41 的 else 分支；
  epd_send.py 仅在 --image2 存在时才拼接，否则 raw = 单面），设备拿到一份自行同显——**限值就是单面的 262144 bit**。
- 预算换算：异显时每面平均约 131072 bit（16KB）；对 384000 B 原始，门槛压缩比从 5.86:1 升到 **11.7:1**。
- 别指望"两面相同压得小"：LZ77 窗口只有 1024 B，第二份数据距第一份 192000 B，远超窗口，不会互相匹配，
  双面成本 ≈ 两面各自压缩后相加（约 2× 单面）。
- 工具侧守门口径：epd_send.py 与网页版都对**合并后**的流判断（compress(A||B).bits > 262144 即拒绝），超限后果与单面相同。
### 6.1 未压缩通道（compress_type=0）

    INIT:      [00, 06, epd_index]
    PIC_INFO:  [01, 00, 00, EE, 02, 00]      // 192000 = 0x0002EE00，字节数非比特数
    PIC_DATA:  192000 字节原样写 ff02，244 B/包，40 ms 间隔 → 787 包 ≈ 31.5 s/面

- 源码有此分支（BluetoothTool.java:41/55），第三方称在其设备上跑通；
- **本机 YSBadge2 实测不可用**（2026-10-21，7 组对照）：数据全收、连接不断，但**从不刷新**；
  长度按字节（192000）或按比特（1536000）声明表现一致，说明固件未进入解码路径；
  副作用：192000 字节后设备 GATT 常变得无响应（UPDATE 写入 Unreachable），需断电重启；
- 推断：接收侧缓冲仅约 32 KB，与压缩模式的 262144 bit 上限吻合，未压缩数据直接打爆接收侧
  （2026-10-21 已在 §6.0 升级为定性结论：BLE 接收路径的一次性缓冲，根源是主控 RAM）；
- 结论：该通道在本机**关闭**，照片抖动仍不可用。完整实验见 LESSONS.md §1。

## 7. 勘误（相对早期版本）
早期 PROTOCOL.md 曾推测：
- 帧为 [00 00 CRC_hi CRC_lo opcode payload]（CRC-16/MODBUS）
- 存在 DEVICE_VERIFICATION 与 UPDATE 步骤
实测 BLE 路径均不成立：
- INIT/PIC_INFO 就是 3/6 字节，无 CRC
- 无 DEV_AUTH、无 UPDATE（BLE）
- 图片必须先 LZ77 压缩，len 填的是压缩后的比特数

## 8. ff04 回执实测（2026-10-21 标定）

ff04 有两个用途，都实测确认：

1. **read 恒为固定字符串** `4a 61 63 6b 20 57 61 6e 67`（ASCII "Jack Wang"，9 字节），与状态无关，不是寄存器。
2. **notify 只在 PIC_INFO 之后触发**，是唯一的状态反馈：

| 触发条件 | ff04 notify | 出现时机 |
|---|---|---|
| 仅连接、不写数据 | 无 | — |
| 只写 INIT | 无 | — |
| INIT + PIC_INFO | `02 00 00` | INFO 后约 175ms |
| PIC_INFO 后 2.5s 未收到数据 | `00 02` | 约 +2.5s |
| 声明 8000bit 只发 200B | `02 00 00` 后 `00 02` | 超时同上 |
| 完整投图（数据及时） | `02 00 00`，随后约 38s 再一个 `00 00` | 见 §8.0 |
| 完整投图 + UPDATE(03 00) | `02 00 00` + 约 38s 后 `00 00` | UPDATE 无独立回执 |

结论：`02 00 00` = 信息已接收、开始等数据；`00 02` = 等数据超时。没有逐块 ACK。

### 8.0 勘误：**存在“刷新完成”回执**（2026-10-22 实测）

早期结论“没有完成回执、只能看屏幕”是**错的**——历史实验每次只保持连接 20-25s，
从未等到那个帧。实测（`_verify/send_probe.py`，2026-10-22 两个数据点）：

| 实验 | `02 00 00` | 数据发完 | `00 00` | 距数据发完 |
|---|---|---|---|---|
| 带 A0 | 4.01s | 5.66s | 43.19s | 37.5s |
| 不带 A0（消歧） | 10.63s | 12.28s | 50.20s | 37.9s |

- `00 00` 在**发完数据约 38s 后**出现，与 A0 无关（消歧实验不发 A0 同样出现），
  时长与电子纸刷新耗时吻合——即 README 约束 4“两次刷新间隔约 30s”的由来。
- **实用价值**：投图后保持连接 ≥45s，即可拿到“刷新完成”的确定性信号，不必再看屏幕猜。
- 另测（同批实验，**待验**）：数据发完后补发 `A0`(START_SENDING) 疑似会触发一次冗余的面板刷新
  （人工观测“有 A0 刷两次、无 A0 刷一次”）。该结论仅凭目视、且观测指引不明确导致回答存疑，
  复测时需先给观察指引；ff04 侧证据（`00 00` 与 A0 无关）是确定的。
- 单独发 `A0`/`A1` 且无数据时：完全无行为、无回执（Step 1/2，确定）。

### 8.1 App 侧怎么用（源码印证）

- `BluetoothTool.java:143` 订阅 ff04；`onCharacteristicChanged` 只有一句 `Log.e("收到Notify：" + data[0])`（:158），不解析、不分支、不改变流程。
- 官方判成功的依据是分包写回调里 `current == total`（数据发完），随后 sleep 1s 直接 disconnect；设备是否真的刷新成功，App 并不知道。
- 因此 ff04 是厂商 SDK 模板遗留的状态通道：写命令有“已收到/数据超时”两种回报，读口是一个写死的字符串 `Jack Wang`（疑为开发者名，调试残留）。投图工具不必订阅它；需要健壮性时，用“设备是否仍在广播”做存活检测更实际。
- 但注意 §8.0：**厂商 App 自己在收到数据后 1s 就断开，所以它永远看不到 38s 后的 `00 00`**——
  “没有完成回执”是 App 行为造成的假象，不是设备能力。

## 9. 会让设备失联的危险输入（实测，需断电恢复）

| 输入 | 现象 | 恢复方式 |
|---|---|---|
| INIT epd_index=9（非法索引） | 连接超时，随后广播消失 | 断电重启 |
| PIC_INFO 声明 272000 bit、实发 34000B | 发送中途连接断开，广播消失，90s 无自恢复 | 断电重启 |

注意：非法 epd_index 在发 INIT 的瞬间就挂，不需要后续数据。超限 payload 会撑爆接收缓冲，比"静默丢弃"严重得多——设备直接掉线且不再广播，所以务必保证压缩后 <= 262144 bit。

适用范围：以上长度约束仅对 compress_type=1（压缩）成立；compress_type=0 时 len 是原始字节数，见 §6.1。

### 9.1 运维教训：扫描不到 ≠ 设备失联（2026-10-21 实测）

设备**间歇性广播**，窗口很短。tools/watch_ble.py 盯 20s 看不到 EE:96:BB:1E:05:28 是常事，
同一时刻换 40s 窗口就能找到（实例：23:16 的 20s 窗口 NONE，23:17 的 40s 窗口立刻 FOUND，
rssi -51）。判断设备是否真的失联，至少看 40s 以上，或改用 tools/scan_ble.py 全量扫描核对。
真正失联的特征是：长时间（分钟级）多轮扫描都无广播，且此时按 RESET/拔插电池可恢复。

**2026-10-21 实机确认**：index 7（双面异显）在压缩模式下可用。A/B 两面各一张 800x480 简图
（红条大字 A / 蓝条大字 B），pic_data = A||B = 384000 B，压缩后 7883 B / 63063 bit，
ff04 回 `02 00 00` 后 33 块发完，两面分别正确显示。限制仍是合并后的 262144 bit。
