# 图片与网页出图工艺（7 色 800×480）

面向“要投到屏幕上”的图，不是面向显示器。所有数字均为实测或可复现参数。

## 1. 尺寸策略

目标固定 800×480（5:3）。

| 策略 | 行为 | 适用 |
| --- | --- | --- |
| contain（默认） | 等比缩放 + 白边 | 不能裁内容的图 |
| fill / cover | 等比缩放 + 居中裁切 | 照片 |
| stretch | 强制拉伸 | 仅当源宽正好 800、宁可纵向压缩也不裁 |
| exact | 非 800×480 直接拒绝 | 已设计好的网页截图 |

源图大于 800×480 时小字必糊，靠锐化只能救回一部分；小字优先在源图上按 1:1 设计。

## 2. 量化：先按内容选抖动

| 内容 | 抖动 | 原因 |
| --- | --- | --- |
| 照片（天空、肤色、水面、阴影） | Floyd–Steinberg | 用 7 色网点模拟中间色，保住层次 |
| 网页、表格、二维码、线稿、大字 | 关闭 | 边缘清晰优先，抖动会在字边撒噪点 |
| 纯色块为主的海报 | 无所谓 | 平坦区误差为 0，抖动几乎不涨体积（见 §7） |

压缩模式下抖动与否直接决定能否发送；未压缩模式下只影响观感与传输时长。

## 3. 量化实现（PIL 快路径）

```python
pal = Image.new("P", (1, 1))
flat = [c for rgb in PALETTE for c in rgb]
flat += [0] * (768 - len(flat))
pal.putpalette(flat)                      # 只放 7 个色，其余补 0
mode = Image.Dither.FLOYDSTEINBERG if dither else Image.Dither.NONE
q = image.quantize(palette=pal, dither=mode)
```

- 误差在 7 色调色板上扩散，语义与 APK `BMPConverter.floydSteinbergDither` 一致。
- 已在 `epd_send.encode_image` 落地（`palette_image()` + `pack_indexed()`）。
- 量化后是 P 模式，像素就是调色板索引，可直接 `(hi<<4)|lo` 打包，无需再逐像素求最近色。
- 实测（800×480，照片源）：手写 Python 误差扩散 2.6 s → PIL 0.42 s；测试图 2.2 s → 0.05 s。
  量化保真度不变：与原图 MAE 77.55 vs 77.53，色板分布逐色差 < 3%。
  差异只是噪声图案不同（FS 本身是混沌的），不代表画质下降。
- 内存也从「每像素 3 个 Python float 的嵌套 list」降到 Pillow 的连续缓冲。
- 现在整条链路（照片）约 1.1 s：抖动 0.42 s + LZ77 0.65 s，两端都不再是瓶颈。

## 4. 两个必踩的坑（已在 epd_send.build_canvas 实现）

1. **EXIF 方向**：手机照片带旋转标记，`Image.open().convert("RGB")` 不会转正。
   必须先 `ImageOps.exif_transpose()`，否则竖拍照片躺倒。
2. **透明底**：对 RGBA 直接 `convert("RGB")` 会把透明区变**黑**（网页截图、图标、PNG 模板）。
   正确做法是合成到白底：`Image.new("RGBA", size, (255,255,255,255)).alpha_composite(src)`。

## 5. 温和预补偿

七色屏比 LCD 丢局部对比与细节，但源图往往已经饱和，补偿要克制（对方实测参数）：

```
Contrast 1.08 → Brightness 1.03 → UnsharpMask(radius=0.8, percent=115, threshold=3)
```

顺序有意义：先拉开明暗，再提亮，最后锐化。幅度再大就出现过冲白边和假色。

## 6. 设计期约束（做网页/模板时）

- 只用 7 原色 + 白底，不要用“接近的颜色”。
- 禁渐变、阴影、半透明、1px 细灰线：抗锯齿产生的灰会在量化时并成黑或白，等于自己毁掉线条。
- 文字对比度要拉到极限（黑字白底 / 白字黑底），字号宁大勿小。
- 版式留白按“远看”设计：桌牌一般 1 m 外被读。

## 7. 体积实测（本项目 LZ77，压缩模式）

> 门槛与完整实测阶梯见 docs/PROTOCOL.md §6.2：原始固定 192000 B，压到 ≤32768 B（压缩比 ≥5.86:1）
> 才送得进去；该上限是**固件 BLE 接收缓冲**的限制，不是屏幕的限制（§6.0）。

| 内容 | no-dither | FS 抖动 |
| --- | ---: | ---: |
| 800×480 日历截图 | 93150 bit / 11.4 KB | 103719 bit / 12.7 KB |
| 800×480 合成渐变 | 30153 bit / 3.7 KB | 992785 bit / 121.2 KB |

上限 262144 bit。截图类无论抖不抖都在限内，照片类一抖就爆——这就是需要未压缩通道的原因
（见 `LESSONS.md` §1）。

## 8. HTML → 屏幕

单文件网页，画布严格 800×480，天气等数据用免密钥接口（如 Open-Meteo），
设计期遵守 §6。截图后直接 `--no-dither`：

```bash
chrome --headless=new --hide-scrollbars --force-device-scale-factor=1 \
       --window-size=800,480 --virtual-time-budget=3000 \
       --screenshot=calendar.png "http://localhost:8080/"
```

- `--force-device-scale-factor=1`：否则高分屏截出 1600×960。
- `--hide-scrollbars`：否则右侧少 15px，整图被压。
- `--virtual-time-budget=3000`：等 JS 取完天气再截，否则截到空数据。
- 截图后必须走 `--no-dither`，让文字边缘落到纯黑/纯白。

## 9. 姓名标签

左上角白底圆角块 + 黑字 + 左侧橙色竖条，字号约 58px（800×480 下 3~4 字最佳）。
用 `draw.textbbox` 量宽高再定底板，不要估算；中文字体走候选列表回退（macOS STHeiti /
Hiragino，Linux Noto CJK，Windows msyh）。

## 10. 屏体工艺约束（GDEY073D46，2026-10-23 调研）

屏体已由规格匹配推断为 **GDEY073D46**（7.3 寸 ACeP，800x480 七色；HARDWARE.md §7，推断待丝印
确认）。以下约束直接决定「怎么画才好看、才发得出去」：

| 约束 | 数值/性质 | 对出图的要求 |
| --- | --- | --- |
| 满刷时间 | **32s**（微雪同款标 35s） | 每次上屏都是 32s 满刷、**没有局刷**——不存在「先出个大概再细化」的路径，必须一次画对 |
| 刷新窗口 | 约 32s 内设备吞数据（PROTOCOL.md §6.0 / §9.1） | 连续投图/轮播条间必须等回执（网页版队列已实现，`00 00` 约 38s 到） |
| 工作温度 | **15~35°C** | 低于 15°C 刷新可能变慢或出残影；北京秋冬室外使用要留意 |
| 呈色 | 七色 ACeP，色滤片反射呈色 | 见下 |

ACeP 呈色特性（数据手册 + 生态经验，均他机级）：

1. **色序是发送方约定的**。GxEPD2 的 ACeP canonical 色序为 0黑 1红 2绿 3橙 4黄 5蓝 6白，
   与本项目实测的 0黑 1白 2绿 3蓝 4红 5黄 6橙 **不同**——本项目以本机实测为准，不要照抄任何库。
2. **扁平色块最佳**。厂商自己的图像生产流程就是 256 色 indexed BMP；色块边缘干净、量化无损、
   LZ77 压缩比高（天气卡实测：扁平设计 84,577 bit，仅占 32% 上限）。
3. **照片要配好抖动**。cale-idf / CALE.es 的经验：七色 ACeP 做招牌很好，写真「意外地够用」，
   但必须配好的抖动。本项目实测照片 + FS 抖动约 155KB 直接超限（§7）——照片路线在本设备上
   基本走不通，除非先解决 32KB。
4. **黄色偏色陷阱**。GxEPD2 + GDEY073D46 上全尺寸抖动图出现过黄色蒙层（Arduino 论坛 2023，
   作者改 HSV 判别缓解）——七色误差扩散对调色板选择很敏感。本项目 FS 走 PIL 语义（§3），
   不碰 GxEPD2 的判别逻辑。
5. **面板内部是双平面**（black plane + color plane，各 1 B/px，共 768000 B）。我们线上发的
   4bit/px（192000 B）是 PC 侧编码，设备解压后还要展开成双平面推给屏——这是 §6.0
   「MCU 只持一批 + 解压窗口」的又一层佐证。

做图清单：800x480 画布；只用 7 个调色板色；字号 >=30px；色块分区；文字走纯黑纯白；
避开细灰线/渐变/密集纹理（既压不动又容易偏色）；发送前 `--offline` 看体积。
