# 安全预案：BLE 路径突破 32KB 传输上限（实验计划）

> 状态：**计划中，未执行**。依据 docs/PROTOCOL.md §6.0 的推论——NFC 路径用
> START_SENDING(0xA0) + 轮询 BUFFER_EMPTY(0xA1) 做 9360 B/批的分批接收，证明设备
> **能**接收超过 32KB 的整图；BLE 路径没有这个握手，所以整条流必须一次装进 ~32KB 缓冲。
> 本实验要验证：BLE 固件是否也实现这套握手。
>
> 风险等级：**高**（已知最坏后果是设备失联需断电重启；不排除未知副作用）。
> 本实验**只写 GATT 特征值**，不涉及固件升级 / DFU / flash 写入（设备也无 DFU 通道），
> 因此不会变砖；但会中断设备使用，需要预约时间并全程人工在场。

## 1. 目标与判据

| 项 | 内容 |
| --- | --- |
| 主假设 | BLE 路径固件实现了 START_SENDING / BUFFER_EMPTY 语义（或等价机制） |
| 成功判据 | 用分批 + 排空握手发出 **> 262144 bit** 的图，屏幕正确刷新，且设备未失联 |
| 失败判据 | 任一步出现 §6 的中止条件；或握手命令无任何可观测响应 |
| 次要收获 | 即使不能突破，也能标定 BLE 上 0xA0/0xA1 的真实行为（写进 PROTOCOL.md） |

**注意：成功判据依赖“屏幕是否正确刷新”，执行方看不到屏幕，所以每一步都必须由人工确认后才会继续。**

## 2. 已知与未知（决定实验怎么设计）

| 类别 | 内容 |
| --- | --- |
| 已知（本机实测） | BLE 命令帧 opcode 在首字节：INIT 00 06 idx、PIC_INFO 01 ctype len×4、UPDATE 03 00 |
| 已知（源码） | NFC 路径：APDU 包装 D0 CF <opcode> …、PACKET_SIZE=240、每 39 包（9360 B）发一次 START_SENDING，然后轮询 BUFFER_EMPTY 直到返回 90 00（NfcDataHandler.java:76/260/274-288） |
| 已知（源码） | EPD_CMD_START_SENDING = 0xA0、EPD_CMD_BUFFER_EMPTY = 0xA1（EPD_Config.java） |
| **未知** | BLE 上这两个 opcode 的帧格式、参数含义、是否存在、以及是否安全 |
| **未知** | BLE 固件在 PIC_INFO 之后是否本来就在“边收边解”（若如此，32KB 就是解压窗口限制而非接收缓冲限制，实验假设不成立） |

未知参数是最大的风险来源：PROTOCOL.md §9 记录过“非法 epd_index 在发帧瞬间就挂”，
所以**不能凭猜测批量构造帧**，必须单变量、小步探。

## 3. 前置条件（全部满足才开始）

1. 设备可断电重启：电池可拔，或 RESET 键可及（HARDWARE.md §3）
2. 设备当前在广播：tools/watch_ble.py 40 连续 40s 内找到 EE:96:BB:1E:05:28
3. 距上次成功投图 **> 30s**（刷新间隔，README 约束 4）
4. 已记录当前屏幕内容（拍照），用于对比“是否刷新”
5. 人工操作者就在设备旁，能看屏幕、能断电
6. 实验前先用 §4 Step 0 确认链路与观测手段正常

## 4. 实验阶梯（严格单变量，从最安全到最危险）

每一步结束后：**等 ≥30s → 确认设备仍在广播 → 人工确认屏幕状态 → 记录 → 才决定是否继续。**

| 步骤 | 动作 | 观测重点 | 中止条件 |
| --- | --- | --- | --- |
| **0 基线** | send_probe.py 发一张已知小图（test_pattern，46216 bit） | ff04 回 02 00 00、屏幕刷新、设备不断 | 任何异常 → 停止，先修观测手段 |
| **1 空探 0xA0** | 不连数据，只往 ff03 写 A0（及参数变体 A0 00、A0 00 00） | ff04 是否出现新通知帧；设备是否仍在广播 | 停止广播 / 写入异常 → 断电重启，记录 |
| **2 空探 0xA1** | 写 A1 及参数变体 | 是否读到/通知到缓冲状态；ff04 帧型 | 同上 |
| **3 小图 + 0xA0** | 正常发一张小图（≤32KB），发完补 A0 | 刷新行为是否改变（提前/延迟/重复刷新） | 同上 |
| **4 分批试跑** | 一张 > 32KB 的图，按 9360 B/批写 ff02，每批后 A0 + 轮询 A1 | 是否出现“等排空”行为（写入变慢 / ff04 变化） | 同上 |
| **5 完整突破** | 同 Step 4，图放到约 2× 上限（约 60KB），全程记录 | 屏幕是否正确显示完整图 | 同上 |

**规则**：

- 同一时刻只改变一个变量（帧格式 / 批次大小 / 图内容）
- 任何一步失败后**不叠加**新的未知操作，退回上一个已知良好状态
- 禁止“连发多个未知命令看哪个管用”——这正是 §9 里那次瞬间挂机的成因
- Step 4/5 之前必须已确认 Step 1-3 至少无害

## 5. 观测手段（每步都要留痕）

- **ff04 通知**：全程订阅，记录时间戳 + hex（已知 02 00 00 = 收到 INFO、00 02 = 等数据超时）
- **广播状态**：每步后 40s 窗口扫描
- **写入结果**：ff03 用带响应写，失败立刻可见；ff02 记录每块是否抛错
- **屏幕**：人工拍照对比（成功与否的最终判据）
- **日志**：探针脚本统一输出带时间戳的日志文件，便于回溯

## 6. 中止条件（出现任一，立即停止）

1. 设备停止广播（多轮 40s 扫描均无）
2. 写入抛异常（GATT Unreachable / 超时）
3. ff04 出现**从未记录过**的通知帧型
4. 连续两步没有任何可观测响应（说明假设可能不成立，继续只是耗风险）
5. 人工操作者视线离开设备（无法确认屏幕状态时不许继续）

## 7. 恢复预案（SOP）

1. **停止**所有写入，不要重试
2. **断电重启**：拔电池 5s 后重接，或按 RESET
3. **验证恢复**：40s 扫描应重新发现设备；随后用 Step 0 的已知小图投图，确认能正常刷新
4. **记录**：失联时的操作、恢复耗时、重启后是否完全正常——这些数据要回写 PROTOCOL.md §9
5. 若重启后仍无广播：等 2 分钟再扫（可能是休眠），仍无则检查电池

## 8. 数据记录模板（每步一份）

    步骤 / 时间：
    发送帧 hex：
    ff04 通知（时间戳 + hex）：
    ff02 写入是否报错：
    屏幕状态（人工）：刷新 / 未变 / 异常
    广播状态（40s 扫描）：
    结论：继续 / 中止 / 回退

## 9. 结论落地（实验结束后必须做）

- 无论成败，把 0xA0/0xA1 在 BLE 上的真实行为写进 docs/PROTOCOL.md（新增小节或 §5.2 扩展）
- 成功 → 更新 §6.0 的“推论（待验）”、§6.2 的门槛说明、README 约束 1、LESSONS.md §6 划掉该项
- 失败 → 在 §6.0 注明“BLE 未实现该握手”，并把失败时的帧与现象记为反向证据
- 全程日志归档到 _verify/，探针脚本登记进 _verify/INDEX.md

## 10. 明确不做的事

- 不写 flash、不碰 OTA/DFU、不动 NFC 路径
- 不在没有人工确认屏幕状态的情况下自动连续发送
- 不把未知命令当作“重试手段”
- 不在设备刷新后 30s 内开始新实验
